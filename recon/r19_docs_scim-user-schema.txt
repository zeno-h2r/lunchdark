The value must be a valid email address and must be unique within the account. Each email object can include:\nvalue (string, required): Email address.\nprimary (boolean): Whether this is the primary email.\ntype (string): Email type (for example, “work”).\nEmail (not userName) is required\nWhile the SCIM 2.0 standard typically requires userName, the LaunchDarkly implementation requires emails instead. The userName field is optional and defaults to the email address if not provided. Most identity providers (IdPs) should map their unique identifier to the userName field for proper user matching.\n​\nOptional and behavioral fields\nField\tType\tDescription\nuserName\tString\tRecommended. While SCIM standards typically require this, LaunchDarkly relies on email as the primary identifier. If userName is omitted, the API defaults it to the email address. The value is in lowercase and trimmed.\nactive\tBoolean\tDefault: true. Set to false to deactivate the user (revoke access).\nexternalId\tString\tIdentifier from the IdP. Used to map users between systems.\nname\tObject\tA complex object containing:\ngivenName (string, max 256 chars): First name.\nfamilyName (string, max 256 chars): Last name.\n​\nLaunchDarkly extension attributes (roles)\nLaunchDarkly lets you define roles using either the standard extension namespace or root-level attributes for convenience.\nField\tType\tDescription\nrole\tString\tThe built-in role: \"reader\", \"writer\", \"admin\", or \"noAccess\". Default: \"reader\" (or the Security Assertion Markup Language (SAML) default role if configured). Cannot be \"owner\" on create/update.\ncustomRole\tString\tA comma-separated list of custom role keys (for example, \"qa-team,release-mgr\").\ncustomRolesArray\tArray\tAn array of custom role keys (for example, [\"qa-team\", \"release-mgr\"]).\nRoot-level fields, such as role, take precedence over fields that are nested in the extension namespace. If both customRolesArray and customRole are provided, customRolesArray takes precedence.\nYou can also use the extension namespace format, which is useful for IdPs like Azure Entra ID:\n{\n  \"schemas\": [\n    \"urn:ietf:params:scim:schemas:core:2.0:User\",\n    \"urn:ietf:params:scim:schemas:extension:launchdarkly:2.0:User\"\n  ],\n  \"emails\": [{\"value\": \"user@example.com\"}],\n  \"urn:ietf:params:scim:schemas:extension:launchdarkly:2.0:User\": {\n    \"role\": \"admin\",\n    \"customRole\": \"custom-role-1\"\n  }\n}\n\nYou cannot create new custom attributes using the SCIM API, but you can set the role and customRole attributes for SCIM users. For SAML-based single sign-on (SSO), LaunchDarkly supports mapping only the role, customRole, and teamKey attributes.\nTo learn more about these attributes, read Roles.\nFor an in-depth guide on how to use custom roles with IdPs, read Creating roles.\n​\nRead-only fields in responses\nThe following fields are automatically generated by LaunchDarkly and cannot be set or modified:\nField\tType\tDescription\nid\tString\tThe LaunchDarkly member ID, used for updates and deletes. This ID is permanent, and does not change even if the member’s email address changes.\nschemas\tArray\tAn Array of SCIM schema identifiers\nmeta\tObject\tA Metadata object containing:\nresourceType: Resource type (for example, “User”).\ncreated: Creation timestamp (Unix milliseconds).\nlastModified: Last modification timestamp (Unix milliseconds).\nlocation: URL to fetch this resource.\nversion: Version number.\nSCIM API endpoints\nPrevious\nSCIM user request examples\nNext"
